# 各阶段的方法

本文按一轮评估的阶段 (建表, 调用知识, client的表示, **枚举**, 渲染和运行, 分组, 机械分诊和确认, 回归, 可信代码) 讲每一阶段用了什么方法: 先说它解决什么问题, 再说做法的要点和为什么这样做. 只写有想法的部分, 常规的 (读文件, 调命令, 汇总) 略去; 也不写到函数和选项的层次, 那些在[design.md](design.md)和代码的注释中. 第4节 (client的枚举) 是重点, 写得最细.

文中"前身"指`../vostd-client-synthesizer`, 它的`docs/enumeration.md`, `triage.md`, `representation.md`记录了每个决定的实验和测量; 本文只取结论.

## 0. 总的思路

**问题.** Verus中调用者对一次调用所知道的只有被调用者的requires和ensures. 规格不够用 (缺ensures, 没转发下层的事实, 缺框架条件) 时被调用者照样验证通过, 要等到有人按真实用法写调用者才暴露. vostd的大多数API还没有已验证的调用者.

**做法.** 替真实调用者写调用者 (client): 机械地生成调用API, 再调用下一个, 再断言下一个调用的requires的程序, 让Verus验证; 证不下去的那条子句是规格缺陷的候选; 给规格补上修改之后client通过, 整个crate仍0 errors, 就确认了缺陷和修法.

贯穿各阶段的三条方法论:

1. **先表示, 后程序.** API表, client, 知识, 结果都是S表达式; 只有渲染一步知道Verus的写法. 所有分析 (切片, 归因, 证否, 换写法) 都在表示上做, 不在渲染出的文本上做.
2. **工具给事实, 人/LLM给判断, 判断写下的东西再被机械地核对.** 表由探针核对, 知识由名字/锚/指纹核对, 修改由整个crate的验证核对.
3. **规则而不是修补.** 从删光数据重新做应得到同样的结论 (原则10); 每处人工修补都是漂移的来源, 要换成由原则推出的机械规则.

## 1. 建表: 源码与VIR按跨度对齐, 探针核对

**问题.** 生成client要知道每个API的签名, 模式 (exec/proof/spec), ghost参数, requires. VIR名字解析完整但丢了很多东西 (生命周期, 自动引用/解引用, `Tracked`包装, trait实现上的requires, 子句的源码写法); 源码 (verus_syn) 写法完整但名字没有解析.

**做法.**

- **两个来源按跨度对齐, 而不是按名字猜.** item-index (用检出里的verus_syn编译) 给出源码的每个条目和每条子句的跨度, 与VIR中跨度相同的结点对上: 写法取源码, 被调用的项, 常量, 绑定变量的类型, `Tracked`包装取VIR. mm和sync的2118条requires中1943条这样得来; 其余 (没有源码的条目, vstd的trait, 宏) 才由VIR写回, 写回有一组规则 (design.md 4.2).
- **翻译不了的子句** (`match`, 闭包) 保留为**模板**: 源码文本, 其中参数的自由出现是洞, 可以代入和渲染; 提升, 求变量只看洞.
- **取哪些API**: 可见范围超出所属模块的 (`pub`, `pub(crate)`, `pub(super)`..), 因为client放在兄弟模块 (第5节). trait的默认方法在每个impl上的继承实例也进表 (可能在那个impl上不可调用).
- **探针 (probe).** 每个条目一个client: 参数与声明完全相同, 于是条目的requires被提升为client的假定, 体是一次调用. Verus的回答直接说明表哪里不对: 编译错误 = 签名错; 前提失败 = 表的requires比源码弱; 空洞 = requires矛盾. **表的requires比源码强时探针发现不了**, 所以表只抄不改.
  - 空洞再分两种: 去掉调用的变体也空洞 → 声明的requires互相矛盾; 变体不空洞 → 调用之后才矛盾 (ensures在这些requires下推出false, 或可信代码过强). 后者是事实, 不能当作表写错.
  - `none-vacuous`: 对每个tracked `Option`参数给`None`, 只留提升出的requires跑一次; 空洞则枚举时不给这个`None` (要求写在spec函数里, 文本上看不出, 只能问Verus).
- **只有机械的修补层.** 采纳rustc的单一建议 (import, 缺的约束, `'static`), 再经探针; 只用探针为`ok`的条目. 不再有手写的覆盖表.
- **表绑定在提交上.** 每张表记`(at COMMIT)`, 与检出的HEAD不一致时一切运行被拒绝. 表过时会使结果误导, 而探针查不出"表比源码强".

## 2. 调用知识: 三种用法严格分开, 漂移分层核对

**问题.** 有些东西表中没有: 哪些参数扮演什么角色 (读者的owner不能给写者), 真实调用者的调用序列, 注释声称的性质, 调用者可假定的事实 (引用计数不饱和). 它们由LLM从注释, vostd的调用点, ktest, 上游Asterinas起草, 可能是错的.

**做法.**

- **知识按用途分三类, 不混用**:
  - 当作**假设去检验**: `claim` (断言注释声称的性质), `protocol` (真实的调用序列). 它们失败就是候选.
  - 当作**过滤或标签**: `role`, `assume`, `prefer`, `limitation`, `not-defect`. 只缩小选择或给失败加标签, 不删去client, 不当作判定.
  - 当作**API的判断**: `must-close` (哪些类型的值必须按值交出, 如锁的guard). 它改变生成, 所以被检查.
- **漂移的核对按"过时了会怎样"决定强弱.** 知识可以落后于检出 (只使种子和标签变弱, 不会使"通过"变得不可信), 但要如实记录核对时的状态:
  - `(at COMMIT)`: 核对时的提交.
  - **规格指纹**: 条目提到的每个API的规格的**源码文本** (文档注释, 属性, 签名, requires/ensures; 不含函数体) 的哈希. 不取VIR, 因为VIR的打印随Verus变.
  - **锚**: 出处带所引那一行的文字, 行号移动时凭它找回 (可机械地改写), 找不到就失去依据.
  - 读过才`--accept`, 写入新的提交和指纹.
- **名字跟着源码走 (`rename-by-key`).** 知识, 证人, 判定, 修改都按VIR名 (`impl&%5::from_unused`) 记, 而impl编号随提交变. 按源码的键 (`Frame<M>::from_unused`) 把旧名映射到新名; 键找不到时退一步, 用去掉全部泛型实参的键, 只在新旧两边都恰有一个时采用. trait或名字变了的仍报出, 由人看.

## 3. client的表示, 良构性, client的requires

### 3.1 表示

client = 参数 + 语句树: 绑定一个调用, ghost快照, 断言, 逐条断言某个调用的requires, `if-let`/`if`的分支. 返回`Result`/`Option`的调用后接`if-let`, then分支继续枚举, else分支至多再几次调用. 返回元组的立即解开, 分量各自成为变量 (`into_raw`的指针和权限分别给`from_raw`). 每条语句有id (`s2.4.e1/1`: 语句2的then分支中语句4的else分支第1句的第1条子句), 后面的分组和连锁失败都靠它定先后.

### 3.2 便宜的良构性在生成时保证

逐条语句检查, 停在第一处不良构: 作用域 (不模拟遮蔽, 否则未关闭的资源悄悄消失), 模式 (exec/tracked/spec), 类型的单向匹配 (被调用者的类型参数可绑定, client的固定), 所有权 (按值传非Copy即移走), 借用 (结果借用那些生命周期能到达结果的引用参数, 由源码的生命周期按省略规则算出; 共享借用使可变的借用者失效; 规格中的使用等同共享借用), 必须关闭的类型 (路径结束时还开着, 用表中只接收它的函数关掉, 而不是丢掉路径).

**方法上的要点: 规则要贴着真实的出错机制写, 不能按"可能出错"写宽.** 拒绝得过宽是无声的 (client消失, 没人抱怨), 拒绝得不够是有声的 (编译错误). 所以每次收紧之后都与基线逐个client比较.

### 3.3 client的requires由提升得出, 不手加

被调用API的每条requires, 代入实参后若只提到**尚未动用**的client参数, 就提升为client的requires; 其余是义务, 由Verus在调用处检查. 于是client的假定恰是"真实调用者开始时必须满足的", 后续调用的前提要由前面调用的ensures负责. 两个有理由的例外:

- **参数的不变式**: 后面的调用要一个已动用的参数`p.inv()`/`p.wf()`, 也作为入口的requires (真实调用者一直持有它传递的资源的不变式). 只限单个参数的无参谓词.
- **新参数与`&mut`参数之间的子句** (`p.wf(*regions)`, p还没被任何调用用过): 提升为入口时的值 (`old(regions)`), 调用处仍断言, 于是问的是前面调用的框架条件. 限制: 被动用过的只能是`&mut`借用过 (按值复制也算用过); 不提升含局部变量的; **一个owner只描述一个对象** (requires中已有同样形式的子句把这些参数与另一对象联系时不提升, 否则路径空洞).

`P ==> may_panic()` (及`allowed_to_panic_if(P)`) 不是义务: 不调用到panic是调用者的选择, 所以在调用之前`assume(!P)`; 不可能时路径空洞, 由空洞断言报出.

## 4. client的枚举 (重点)

### 4.1 演变: 从向前穷举到目标导向

前身的枚举是**向前穷举**: chain从F出发至多K步, 每步试每个API的每种实参组合, 良构就留; 另有flow (F的输出给G), repeat (能否再调用). 测量 (r22, 9850个client) 显示: **5%的client给出全部失败事实** (chain 5770个client只有126种失败). 原因:

- 一个失败的子句出现在所有经过G的序列中, 每种前缀后缀组合都是一个client;
- 与问题无关的调用 (不碰G的实参) 也算不同的client;
- 没有"这个目标已经有client了"的概念, 预算只限数量, 超出时降深度, 丢的可能正是唯一到达某目标的长序列.

改为**目标导向**, 受Clouseau (Zhe Zhou等, PLDI 2026: 由目标事件向后补它依赖的事件) 和覆盖类型 (欠近似的完备性) 的启发, 但依赖不由人写的uHat规格给出, 而由**类型和子句提到的参数**机械地推出.

改之前先做了两步小实验验证依赖规则:

1. **离线切片** (不跑Verus): 把每个失败的client切成目标语句和它依赖的调用. 若把`&mut`共享状态的改动者都算依赖, 几乎切不掉什么 (每个调用都`&mut regions`); 只按**产生者**切, 315个目标只需492个极小切片, 与"5%"一致.
2. **只跑极小切片**: 507个中95.5%在原来的子句失败, 即只靠产生者就重现; 其余4.5%恰是"中间被改过的共享状态" (框架条件) 和"再调用一次". 所以基本目标只放产生者, 干扰单独作为目标, 按需生成.

### 4.2 目标和义务

- **目标** = (API G, G的第i条requires). 目标的集合本身就是枚举的规模: 表中每个API的每条requires一个, 不再乘以序列的组合数.
- **义务** = G的requires子句**提到的**参数. 不被任何子句提到的参数什么也不问, 就来自client的参数 (被提升).
- 每个client回答一个问题: "真实调用者由这些调用得到G的实参之后, 能否满足G的每条requires." G的requires在调用前逐条断言, 于是Verus报出的是具体哪一条.
- **完备性**的定义 (欠近似的"够不够"): 不数client, 而要求每个目标至少有一个client**到达**它 (子句被断言, 且它提到的参数不是被提升的client参数), 或者给出到不了的理由 (无产生者, 产生者的requires不可满足, 超出深度).

### 4.3 一条有界的目标回归 (goal族)

计划 = 以G结束的调用序列 + 因果链: `(out I J)` 第I个调用绑定的值是第J个的实参, `(touch I J)` 两者共享实参. 四种相关性:

| 规则 | 含义 | 预算 |
|---|---|---|
| **R1 产生** | A的输出 (结果, `Ok`/`Some`之内, ghost结果, 元组分量) 能作G的义务参数. A自己的参数一般来自client; 但A的ensures同时提到A的结果和A的某个参数w时, w的来源影响G的子句, w又成为义务 (两步链, 如`clone(self)`再对它给的值调用lemma) | 深度至多2 |
| **R2 触动** | H按`&mut`取G也取的值. 成功分支上只在H**可能改动G的子句所读的**时 (读写集, 见下); **H出错之后总是** (问的是失败之后状态还能不能用) | 至多一次 |
| **R3 再调用** | G按值拿走了实参, 由产生者给新值再调用G; 没有产生者时用新参数 | 至多一次 |
| **R4 由ensures向前** | P的ensures写到的输出或`&mut`实参, 本模块没有读者时, 取表中读它最多的API为读者, 生成P → 读者 | 每个输出一个 |

加上**往返**: 一对A, B (B取A的输出, 给回A实参的类型), 两者的ensures中各有连结果和实参的等式时, 由等式推出要断言的恒等 (`in.range() == out.range()`); 只看类型会生成大半不是往返的client (`slice`再`clone`断言`start_paddr`不变), 所以必须"连结果和实参".

几个机械判定的细节, 都由实验中的错误逼出来:

- **产生者的判定 (`produces?`).** 数据类型按类型和模式流; 整数和spec值**只对子句提到的参数**找产生者 (否则任何返回`usize`的调用都是任何`usize`参数的产生者), 并且要源码中两边写的是同一个非裸整数的类型 (VIR把`Paddr`, `Vaddr`, `usize`都写成`usize`, 只看VIR会把虚拟地址给`pa: Paddr`).
- **两步链的相关性经由G推出.** P没有ensures时 (external, trait函数), "ensures同时提到结果和w"永不成立; 简单地"没有ensures就算相关"会爆炸 (page_prop 462 → 852). 有原则的条件: 只在G的某条子句同时提到P给的参数和另一个与w同类型的参数时, w才是义务, 产生w的F也要取这个类型.
- **读写集 (rw.rkt) 只用来去掉问不出东西的client, 不用来断言失败.** 读: G的子句在变量v的哪些访问路径上应用谓词 (`owner.value().is_frame()`读owner的(value is_frame)). 写: H的ensures在H结果的某个分支上, 对`final(v)`的哪些路径给出了事实, 或框住了它 (`final(v).P() == old(v).P()`; `*final(v) == *old(v)`框住全部). 比较和析取不算给出. 纯语法, 是干扰的过近似; 实测中被判为无干扰的130对都没有失败.
- **分支要按client的结构定**: G在H结果的哪一支上调用, 就只用H在那一支上的ensures (不分支时只用无条件的).
- **配对**: 出错之后的client (goal_err) 只把H的参数配给**角色相容**的G的参数; flow中F的`&mut`执行参数 (F操作的对象) 也可共享给G, 但只在G的requires把它与流过来的值联系起来时; 流过来的是F的ghost结果 (owner) 而G的执行参数是新的、又被G的requires与之联系时不生成 (新对象配别人的owner, 只会失败); 流过来的是值时照常生成 (`split(offset)`的`offset <= self.size()`是调用者自己的选择).
- 计划由**枚举器** (下一节) 实现: 以第一个API的探针为种子, 主路径恰是计划的调用, 接受条件由因果链机械地导出. 所以goal的client与别的族是同一种表示, 可以逐个比较.

效果 (前身r22 → r27): client 9850 → 2865, 失败事实一个不丢且多出新的, 生成从约2分钟到几秒.

### 4.4 枚举器 (enum.rkt): 构造即良构的树搜索

goal和protocol都落到同一个枚举器上. 它的输入是一个枚举规格 (参数, 可调用的API, 提供者, 深度, else深度, 性质, 选项), 输出一组client树.

- **每步加一个调用**, 立即经良构性检查 (第3.2节), 不良构的不展开: client由构造保证良构.
- **分支**: 返回`Result`/`Option`的调用之后`if-let`, then分支继续主路径, else分支至多E个调用.
- **路径结束的条件**: 没有打开的必须关闭的值. 还开着时调用表中只接收它的函数 (`drop`) 关掉, 而不是丢弃路径 (否则guard多在最后一步拿到的模块client少八成).
- **提供者**: 缺少的tracked参数由proof函数 (`Option::tracked_unwrap`等) 从现有资源中取出, 只在没有现成变量时; 提供者的spec参数只由当前调用的接收者形成 (权限为被操作的对象取).
- **性质约束调用序列**: 事件是一次调用 (API名, 角色到变量), 性质是事件上的文法 (正则加递归, 有交和补, 用**Brzozowski导数**求剩余), 按对象切片. 协议的"主路径恰好按序调用"就是一个性质. 剩余文法为空即剪枝.
- **实参的选择有三条规则** (都由协议的噪音测量逼出):
  - `prefer-produced`: 先用前面调用产生的值, 其次提供者从中取的, 新参数只作后备. 先取新参数时, 新参数的requires在`regions`已被动用后提升不了, 协议失败中60/74组是这个.
  - `pair-by-origin`: 每个值记下由哪个调用产生; 用了调用k产生的对象, 类型是k的ghost返回的tracked参数也必须取自k (对象和owner同源), 反之亦然.
  - `consistent-fresh`: 一条requires (代入后) 同时提到未动用的client参数和产生的值时, 这个选择丢掉 (对新参数一无所知, 子句必定证不出).
- **预算**: 每步每个API至多`max-choices`个延续, 协议至多若干client. 协议代表用法, 不是要覆盖的空间.
- **两处剪枝使长协议可行** (都是精确的, client逐项不变):
  - `canonical-combos`: 可互换的新参数按声明次序用; 逐个参数构造实参元组, 被拒绝的前缀不延长 (而不是先造全积再过滤). vm_space 54分钟 → 7分钟.
  - `properties-may-call?`: 展开一个API的全部实参组合之前, 先由只看API名的性质判断它能否是下一次调用 (历史接上至多k次提供者再接这个API). 7分钟 → 78秒.

### 4.5 claim和protocol族

- **claim**: 在API自己的前提下调用, 断言知识中的声称. 声称是**模板** (洞是参数, 结果`ret`, ghost结果`gret`, 快照`old_x`), 不压平为文本, 否则切片和归因看不到其中的变量. claim绑定的名字 (`forall|r|`, `matches Ok(r)`) 与代入进来的名字相撞时先改名, 避免捕获. claim的断言可以读已被按值拿走的变量 (Verus接受spec读取), 但重述requires的断言不可以.
- **protocol**: 知识中的真实调用序列, 参数是各调用探针参数的并 (同名的加位置后缀), 类型参数的约束取并; 主路径恰按序, 默认无else分支; 实参按4.4的三条规则选. 调用了表外API (有记下的原因, 如闭包参数) 的协议不生成, 记为注记.

### 4.6 生成时就去掉的噪音

- **被绑的子句** (`tied`): G的一条子句同时提到G的新参数和前面产生的值, 什么也不能使它成立. 只在一个client中**每条**提到产生值的子句都被绑住时才丢这个client (按"有一条就丢"会丢掉好事实, 如`split`的`self.inv()`); 其余被绑子句的失败标为噪音.
- `may_panic`子句改为`assume(!P)` (3.3).
- 参数的不变式和新参数子句的提升 (3.3).

### 4.7 试过而没有采用的

| 做法 | 为什么不用 |
|---|---|
| chain/flow/repeat向前穷举 | 被goal的R1/R3和计划覆盖; 其余是指数增长的冗余 |
| 由已验证的vostd调用者挖调用序列 (X1, 从VIR) | 有requires的API中只有33%在已验证代码中有调用者; 真实用法大多在未验证的ktest和上游, 要另外解析 |
| 把protocol概括成模板推广到别的模块 (X2) | 能概括的是1–3个调用的短骨架, 正是goal已生成的; 长的真实序列是模块特有的, 一个骨架在别处匹配上百种API组合, 定不出 |
| 两个独立的洞做组合测试 (X6) | 两个以上洞的子句只有21条, 成对覆盖就是全积; 加了"两个产生者"只得到2个client |
| 后条件合成 (post), 按名字插引理重试 (retry) | 前者候选少难判; 后者的问题由证否和provable回答 |
| 省略的生命周期`'_`默认打开 | 正确, 但使某些模块client成倍 (dma_coherent 219 → 810); 是选项, 默认关 |

## 5. 渲染和运行

- **client放在被测模块的兄弟模块** (`<parent>::cs_clients`). Verus让closed的spec函数体和私有字段对**定义模块及其子模块**可见; 前身放在子模块里, client比真实调用者看得多, "结果只由closed函数描述"一类缺陷系统地漏掉 (同一批client移到兄弟模块, segment 25个由通过变失败, 正是已确认的缺陷). 代价: 兄弟仍看得见父模块的closed体; 类型不变式在兄弟中不可用 (与别的模块的调用者一致).
- **导入交给rustc**: 不由VIR的路径拼导入. 模块跑完后, 编译错误中只有一个候选的建议加进本次运行的表, 整个模块重跑, 通过的不减少才采用; 至多3轮 (rustc分阶段报错: 先名字, 后方法所属的trait). 对表自己某行`use`报E0603的, 下一轮去掉 (由重新导出或下一轮建议补). 哪条路径可写不由我们解释Rust的可见性.
- **每个client一个z3** (`#[verifier::spinoff_prover]`): 并行, 不崩溃, 结果不依赖同批的别的client. 线程数按内存估计.
- **可信的结论**: 每个模块一个必定失败的sanity client, 每条路径末尾一个`assert(false)` (空洞性). sanity不是恰好失败一次, 这个模块就没有被真正验证.
- **归因到语句**: 渲染同时给出行映射 (每行属于哪个client的哪条语句); `--expand-errors`把不透明谓词的失败展开到失败的合取项, 归给同一client的第一个错误.
- **故障的处理**: 编译错误使整个模块不被验证 → 去掉有编译错误的client重跑; Verus崩溃不是client的错 → 这批client对半拆开重跑, 递归到下限, 合并.
- **续跑的键**包含一切决定结果的东西: client, 展开后的client, 表的导入, 决定结果的代码 (render, run, module-run, repair的哈希), 检出的状态. 不在键里的代码 (配置, 汇总) 改了不重跑.

## 6. 分组和标签

- **按失败子句的身份分组** (被调用者, 第几条), 不按文本 (文本随变量名变; r23按文本1475组, 按身份807组). 不透明子句按展开后失败的合取项分; 出错之后的client按出错的调用归为一组.
- **连锁失败按路径标出, 不删**: 失败的断言之后Verus假定它成立, 后面的失败可能只是后果. 用语句id的先后, 每组记`(first N)` (多少client中这是路径上第一个失败) 和`(after ..)`. 只是先后不是因果, 所以只排序不删除.
- **已知问题按事实挂上**: claim证人的事实写成"在主体调用的位置上" (`#aI`第I个实参, `#gr`ghost结果..), 任何client中在主体调用之后失败的断言, 换成位置后与之相同, 就挂上这个问题. 这样同一个缺的事实以不同子句出现时也认得出.
- **知识标签只用关于失败的那个API的条目** (用client中任何API的条目会标注一切).
- **判定按组存**, 带责任者和所读规格的指纹; 指纹变了标`stale-verdict`, 算作没有标签.

## 7. 机械分诊和确认

把"是不是缺陷"中能由Verus回答的部分全部机械化, 只留"真实调用者需不需要"给判断.

### 7.1 覆盖 (coverage): 哪些ensures没有client检验

一次带`--log smt`的运行, 每个client一个SMT文件. Verus把F的ensures编成`ens%F(..) = (and c_1 .. c_n)`; 在文本上给每个合取项加守卫`(=> g_j c_j)`, 把`(check-sat)`换成`(check-sat-assuming (g ..))`, 对最后一次查询求unsat core, 再对每个守卫问"它为假其余为真". 不是unsat的, 这个client需要这条子句. 与"删一条子句重跑一轮" (每条一次Verus) 给出同样的子句, 代价是一次运行加几十秒z3. 失败的client什么也不需要; 资源上限记为`limit`, 只被它涉及的子句是`unknown`而不是`unchecked`.

### 7.2 证否 (refute)

把失败的断言P换成¬P再跑同一个client. P没证出, 说明事实与¬P相容; 若¬P证得出, P在每条到达路径上为假 → client的用法不合法, 值的含义不对, 或规格说了相反的话. 证不出 (`open`) 就是"事实决定不了P", 缺事实的候选. 每组只探路径上最先失败的那个client.

### 7.3 归因 (责任者)

按展开后语句的次序, 记下每个变量最后由哪个调用写过 (结果, ghost结果, `&mut`实参, 从它们取出的值; 提供者只转交不算写). 失败子句读的变量中最后被写的那次调用就是**责任者**; 都没被写过的是`entry` (client自己参数的事, 多是被绑的新参数). 这是"该由谁给这个事实"的假设, 由下一步检验.

### 7.4 责任者证得出吗 (provable)

把client失败的子句改写成责任者F的形参写法 (`&mut`传入的写`final(p)`, 结果写F的命名结果, if-let载荷写`res->Some_0`并加`res is Some ==>`, 快照写`old(p)`); 读了F看不到的东西的是`inexpressible`. 在检出的副本中加进F的ensures, 验证整个crate, 去掉证不出的, 再验证, 直到不再去掉. 留下的 = F有这个事实而不给调用者 (最常见的已确认缺陷). 一次分析是一个固定的实验: 所选的组第一次就记下, 续跑试同样的组.

`drops`是同一机制的另一入口: 包装函数F调用G, 把G的ensures搬到F (参数, 结果, ghost结果对上), 留下F证得出的, 再生成claim client在原版上检查调用者是否得不到.

### 7.5 确认 (confirm)

一起证出的子句可能互相帮助, 要逐条单独成立:

- **分槽**: 一个槽中每个函数至多一条, 且没有两条的函数一个调用另一个 (VIR的调用). Verus只按被调用者的规格检查一个函数, 所以无调用关系的子句互不影响, 可在一轮中验证.
- 单独加上时别处**原有的**证明失败, 归给能影响那个函数的查询的子句: 它调用的函数的, 或**同一模块**的 (Verus一个模块一个求解器, 查询变了会扰动脆弱的证明), 记为`breaks-proof` (修改的代价, 不算确认).
- **rests-on**: F的函数体中的`assume`/`admit`, 直接调用的`external_body`函数. 提示, 要读.
- 补丁打上, 以副本为检出重跑调用了被改函数的失败client, 按组前后比较.

### 7.6 手写修改的确认 (fixes)

provable/confirm只能确认"给责任者加一条ensures". 其余修改 (改open spec函数, `dual_spec`改为open, 上下两层一起改) 写成数据: `(fix ID (groups ..) (why ..) (replace FILE OLD NEW) ..)`, OLD在文件中恰好出现一次, 否则`bad-edit`, 不猜. 然后:

1. **一起**: 全部打上, 验证; 错误落在某修改的新文本里就归它, 落在别处就映射回原行号, 由VIR找到所在函数, 归给改了它调用的函数或同模块函数的修改 (`breaks-proof`). 去掉归到的再验证.
2. **retry**: `breaks-proof`只到模块, 会一次去掉同模块的好几个; 被去掉的逐个在留下的之上再试.
3. **alone**: 留下的分槽单独验证.
4. **with**: 单独证不出的, 与它所改函数 (传递地) 调用的函数上**单独成立**的修改一起再验 (上层转发下层新给的事实). 通过即与alone同样算数. 只看调用, 不看同模块 (同模块是扰动, 不是事实的来源).
5. **clients**: 重跑目标组所在模块, 每个目标组前后的client数; `AFTER`数的是**这组原来的client**中仍在这组的加上改为超时的 (超时是未知, 不是通过).
6. **冻结的基线 (`--base`)**: 已确认的修改每次先打上, 不分槽, 不归错, 不能被替换; 新修改在其上分槽; 比较以只打基线的那次重跑为前.
7. **并行副本**: 单槽和with的各次验证互不依赖, 在几份检出中同时做, 每份自己的cargo目标目录.
8. **标记**: `rests-on`有`assume`/`admit`, 新文本带`#[verifier::..]`属性的, 由人决定是否记为已确认.

## 8. 已知问题的回归

- **证人是client本身** (完整的client形式), 不是名字或组键: 重新生成后名字和组会变.
- **期望按子句的身份**: `(fails (requires API N))`或`(fails (claim))`, 不对渲染出的文本写正则.
- 运行方式与评估完全相同. 每个证人的状态机械给出 (`shows`, `passes`, `other`, `vacuous`, `broken`..); 问题在原版上`present`/`gone`/`undetected`/`no-witness`, 在补丁上`fixed`/`not-fixed`. 判据是那条子句, 不是整个client通过 (证人常常还撞着别的问题).

## 9. 可信代码

- **列举只读源码** (git中某提交的文件), 不靠VIR (VIR里没有`external`的东西, `assume`不带语法位置). 一个小词法分析 (注释, 字符串, 字符常量, 原始字符串) 加括号配对就够; 规格中的块由右括号之后跟着什么认出.
- **身份不用行号**: (种类, 文件, 条目路径, 细节), `assume`的细节是它的命题. 判定于是跟得上代码移动.
- **指纹针对判定看到的文本**: 条目的整体 (`external_body`的函数体就是"实际行为"); `assume`/`admit`取所在的整个函数.
- **演示**: 把"过强"的结论写成只用公开条目的Verus代码 (证明`false`或明显错误的事实), 与评估共用运行目录和结果格式.

## 10. 判定的组织

- 一次审阅到底再写修改, `fixes`跑一次, 修补一次; 分几波审会使修改反复替换撤回 (r1中`fixes`跑了7次, 3次是撤回).
- 判定组时读组里的**每个**client: 组按第一个失败的子句分, 同一子句的client可能因不同的原因失败.
- 机械确认了且没有标记的直接记为缺陷; 带标记的, `decision`, 冲突, 汇总后一次问人.
